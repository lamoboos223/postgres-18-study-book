Chapter 10 · EDB: Monitoring and Admin Tools

Logging and the views a DBA actually watches

Monitoring is not a vendor dashboard. It is: who is connected, what they wait on, whether the disk is filling, and whether the logs tell you why.

1. What you need to know

Two channels: logs (postgresql.conf logging) and stats views. Debian often logs via systemd journal and/or files under /var/log/postgresql/.

2. Mental model

pg_stat_activitysessions right now
pg_stat_databasecounters
pg_stat_bgwriter / iowriters & I/O
pg_lockswho blocks whom
log_min_duration_statementslow SQL
df + pg_waldisk

3. Deep explanation

pg_stat_activity.query is the current (or last) statement. wait_event tells you if the session is idle, on a lock, or on IO. state = 'idle in transaction' is a classic production leak — it holds snapshots and blocks VACUUM.

Logging GUCs: logging_collector, log_destination, log_min_duration_statement, log_connections, log_lock_waits. Too much logging can fill disks.

EDB’s GUI slide: pgAdmin 4 is the community admin client (Query Tool, Visual Explain). Postgres Enterprise Manager (PEM) is EDB’s paid dashboard — know the name; this book does not install it. The exam facts are the views and logs above.

PostgreSQL 18 note. pg_stat_io is the detailed I/O stats view (expanded over recent majors). Use it with EXPLAIN (ANALYZE, BUFFERS) — Chapter 11. Do not treat unofficial “2–3× AIO” blog numbers as exam facts.

4. PostgreSQL 18 example

SELECT pid, usename, datname, state, wait_event_type, wait_event, left(query, 80)
FROM pg_stat_activity
WHERE backend_type = 'client backend';

SELECT datname, numbackends, xact_commit, blks_hit, blks_read
FROM pg_stat_database WHERE datname = 'study_lab';

5. Production perspective

🏭 Production note. Alert on: disk, replication lag (Ch 15), oldest xmin / wraparound risk (Ch 13), connection saturation, lock waits. APM is not a substitute for pg_stat_activity.

6. Hands-on lab

sudo -u postgres psql -d postgres -c "SHOW log_destination;"
sudo -u postgres psql -d postgres -c "SHOW logging_collector;"
sudo ls /var/log/postgresql || true
sudo journalctl -u postgresql@18-main -n 30 --no-pager

Turn on slow-query logging for the lab (reload):

sudo -u postgres psql -d postgres -c "ALTER SYSTEM SET log_min_duration_statement = '200ms';"
sudo pg_ctlcluster 18 main reload
sudo -u postgres psql -d study_lab -c "SELECT pg_sleep(0.3);"
ALTER SYSTEM writes postgresql.auto.conf. pg_sleep(0.3) should exceed 200ms and land in the log.

7. Lab verification

sudo grep -i sleep /var/log/postgresql/postgresql-18-main.log | tail
# or journalctl if that file does not exist
sudo -u postgres psql -d postgres -c "SHOW log_min_duration_statement;"

8. Troubleshooting

Symptom

High CPU, few queries in the log.

Investigation

SELECT pid, state, wait_event, query FROM pg_stat_activity;
top -u postgres

Diagnosis

Busy backends with no wait event are on CPU (bad plans, tight loops). Waiting on Lock / LWLock is contention. Waiting on IO is storage.

9. Exam focus

🔥 Exam focus. Name pg_stat_activity, pg_stat_database, pg_locks. Know idle in transaction is dangerous. Reload after logging GUC changes when context is sighup.

10. One-minute revision

  • Activity views + logs + disk.
  • log_min_duration_statement for slow SQL.
  • Reset log_min_duration_statement to default if the log gets noisy.

Review questions

Q1. Why is idle in transaction worse than idle?

An open transaction holds a snapshot. VACUUM cannot remove dead rows still visible to that snapshot. idle is just an unused connection (still costs a process).
