Chapter 16 · Beyond Essentials · Active-active

Master-master is not streaming replication

Chapter 15 is active-passive: one writer, one replica. People still say “master-master” when they mean two writers (active-active). Vanilla PostgreSQL 18 cannot do that with physical streaming. This chapter is vocabulary and why — no extra VM, do not wire a second writer into study_lab.

1. What you need to know

Physical streaming copies the whole cluster by shipping WAL. WAL is a single timeline from one primary. A standby in recovery cannot accept ordinary writes. Promote it and the old primary must stop, or you get split-brain (two timelines, two copies of the truth).

Active-active means two (or more) nodes accept writes and somehow merge. That is a different problem: conflict detection, unique keys, sequences, DDL, and “which UPDATE won.” It is not pg_basebackup -R.

Essentials exam: streaming = one primary. Name the multi-writer product; do not claim you built it.

3. Deep explanation

Why physical streaming cannot be master-master

Each cluster has one control file, one WAL timeline, one set of XIDs. A replica applies someone else’s WAL. If both nodes generate WAL, there is no built-in merge. That is why the docs say primary / standby, not “two masters.”

What people actually mean

PhraseUsually meansPostgres reality
Master-slave / primary-standbyOne writer, replicasChapter 15. Active-passive.
Master-master / multi-writerTwo writers, same dataNot community streaming. PGD / BDR / Citus (different shapes) / app-level sharding.
Logical pub/sub both waysTwo publications, two subscriptionsFragile DIY. Loops, unique-key clashes, sequences collide. Subscriber tables are meant to be treated as read-only.
Failover HA (Patroni, EFM, repmgr)Keep one writer aliveStill active-passive. Faster promote, not two writers.

Why two writers hurt

  • Identity — two nodes both INSERT into an IDENTITY / sequence: same ids, unique violations, or silent duplicates if you “fixed” sequences badly.
  • Same row — A updates price = 10, B updates price = 12 before they see each other. Last-apply-wins is a choice, not physics.
  • DDL — ALTER TABLE on one node while the other writes. Logical apply breaks.
  • Loops — A replicates to B, B replicates the same change back to A unless origin filtering exists.

EDB Postgres Distributed (PGD, formerly BDR)

This is the name the Essentials deck waves at. Multi-node, write on more than one node, conflict handling, often used for geo / always-on. It is not community CREATE SUBSCRIPTION. It is not this lab. HARP sits in front of a PGD/Patroni-style cluster as a routing layer — still not “turn on master-master in postgresql.conf.”

Bidirectional logical replication (know, do not run here)

Community Postgres can publish and subscribe. Two nodes each CREATE PUBLICATION and CREATE SUBSCRIPTION toward the other. That is the closest built-in sketch of master-master. It is not a supported HA pattern for study_lab. If you ever see it in the wild, the minimum extras are: no overlapping sequence ranges, replica identity on every table, and origin filtering so a change does not bounce forever. Still worse than a real multi-writer product for the same row updated on both sides.

-- shape only — do not run against the Chapter 15 standby
-- Node A
CREATE PUBLICATION pub_a FOR TABLE app.users;
CREATE SUBSCRIPTION sub_a CONNECTION 'host=node_b dbname=study_lab' PUBLICATION pub_b;

-- Node B
CREATE PUBLICATION pub_b FOR TABLE app.users;
CREATE SUBSCRIPTION sub_b CONNECTION 'host=node_a dbname=study_lab' PUBLICATION pub_a;
Needs wal_level = logical on both. Do not point this at pg-standby while it is a physical replica — that node is in recovery and cannot be a logical publisher of local writes.
⚠️ Do not “try it” on the book VMs. pg-standby is a physical replica. Dual publication would fight recovery, slots, and the promote drill. Leave Chapter 15 intact.

4. PostgreSQL 18 example

Prove the standby is still not a writer (from Chapter 15):

# on pg-standby
sudo -u postgres psql -d postgres -c "SELECT pg_is_in_recovery();"
# true

sudo -u postgres psql -d study_lab -c "INSERT INTO app.users (email) VALUES ('should-fail@example.com');"
# expected: cannot execute INSERT in a read-only transaction
That error is the whole chapter. Reads may work. Writes do not until you promote — and then the old primary must be fenced.

5. Production perspective

🏭 Production note. Most shops want active-passive plus backups. Multi-writer is for write locality or “no downtime even for writes on a region outage.” It costs conflict design, operational complexity, and usually a vendor stack. Do not buy it to paper over a missing PITR or a forgotten replication slot.

8. Troubleshooting

Symptom

Someone enabled writes on the standby “to make it active-active.”

Diagnosis

If they promoted without fencing the old primary, you have two writers and diverging data. Restore from backup or pick one timeline. You cannot merge two physical clusters.

Symptom

Bidirectional logical replication duplicates rows or unique_violation storms.

Diagnosis

No origin filter (loop), shared sequences, or both sides updating the same PK. This is why the book does not lab it.

9. Exam focus

🔥 Exam focus. Streaming = one primary = active-passive. Promote switches the writer; it does not create two. Logical pub/sub is not multi-master HA. EDB Postgres Distributed / BDR is the named multi-writer product. Patroni / EFM / repmgr still keep a single writer.

10. One-minute revision

  • Ch 15: WAL from one primary. Standby is read-only in recovery.
  • Two writers need conflict rules. Community Postgres does not ship that as streaming.
  • PGD = product name. Do not run dual SUBSCRIPTION on these VMs.

Review questions

Q1. True / False. Set hot_standby = on on both nodes and you have master-master.

False. hot_standby allows reads on a replica in recovery. Writes still belong to one primary.

Q2. You promote pg-standby and forget to stop pg-primary. What is that called?

Split-brain: two writers, two WAL timelines. Not active-active HA.

Q3. Which built-in feature is the closest sketch of two writers, and why is it still not this lab?

Two-way logical publication/subscription. Conflicts, sequence clashes, apply loops. The Chapter 15 standby is a physical replica and cannot publish local writes.

Q4. Name the EDB product for multi-writer Postgres.

EDB Postgres Distributed (PGD), formerly BDR.
