Chapter 9 · EDB: Database Security

Roles, GRANT, and the failed-then-fixed permission lab

Authentication is pg_hba. Authorization is GRANT. Superuser bypasses almost everything — do not use it for the app.

1. What you need to know

Roles can login or be groups (NOLOGIN). Privileges: CONNECT on database, USAGE on schema, table DML rights, and so on. Default privileges on public have tightened across recent majors — never assume “public can do anything.”

3. Deep explanation

SQL Server: login (instance) + user (database). PostgreSQL: one role cluster-wide; you still must grant database CONNECT and object rights. GRANT role_a TO role_b is group membership.

EDB module 9: pg_hba methods to name — trust, peer/ident, scram-sha-256, md5 (legacy), cert, reject. First matching line wins.

Object owner can do almost anything to that object. Superuser can do almost anything to the cluster.

Row Level Security policies

GRANT is table-wide. A policy hides or rejects rows. Enable it first; then create at least one policy. With RLS on and no policy, a non-owner sees zero rows (deny by default).

ALTER TABLE app.notes ENABLE ROW LEVEL SECURITY;

CREATE POLICY name ON table_name
  [ AS { PERMISSIVE | RESTRICTIVE } ]
  [ FOR { ALL | SELECT | INSERT | UPDATE | DELETE } ]
  [ TO { role_name | PUBLIC | CURRENT_USER | SESSION_USER } [, ...] ]
  [ USING ( using_expression ) ]
  [ WITH CHECK ( check_expression ) ];
  • USING — which existing rows you may see / update / delete.
  • WITH CHECK — which new or updated rows you may write.
  • FOR SELECT needs USING only. FOR INSERT needs WITH CHECK only. FOR ALL / UPDATE often need both.
  • PERMISSIVE (default) — matching policies are OR’d. RESTRICTIVE — AND’d on top.
  • Superuser and the table owner bypass policies unless you ALTER TABLE … FORCE ROW LEVEL SECURITY. Role option BYPASSRLS also skips them.

EDB’s slide example: CREATE POLICY account_managers ON accounts TO managers USING (manager = current_user); Same idea on our lab table below. List policies with \d app.notes or SELECT * FROM pg_policies WHERE tablename = 'notes';. Drop with DROP POLICY name ON app.notes;.

Column encryption (pgcrypto)

EDB’s encryption slide is column-level, not SQL Server TDE. Community PostgreSQL does not encrypt the data directory for you. Encrypt selected columns with the pgcrypto extension. Encrypting everything is slow and is not “more secure” by itself — the key still has to live somewhere.

  • One-way — crypt() + gen_salt(). For passwords. You cannot decrypt; you only verify.
  • Two-way — pgp_sym_encrypt() / pgp_sym_decrypt(). For values you must read back (card, SSN). The passphrase is the secret.
CREATE EXTENSION pgcrypto;

4. PostgreSQL 18 example

CREATE ROLE app_user LOGIN PASSWORD 'app_user_lab_only';
GRANT CONNECT ON DATABASE study_lab TO app_user;
GRANT USAGE ON SCHEMA app TO app_user;
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA app TO app_user;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA app TO app_user;
USAGE on a schema is “may look up names.” Without it, even SELECT on a table fails. Sequences need USAGE for IDENTITY/nextval.
CREATE TABLE app.notes (
  id    bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  owner name NOT NULL DEFAULT current_user,
  body  text NOT NULL
);
GRANT SELECT, INSERT, UPDATE, DELETE ON app.notes TO app_user;
GRANT USAGE, SELECT ON SEQUENCE app.notes_id_seq TO app_user;

ALTER TABLE app.notes ENABLE ROW LEVEL SECURITY;

CREATE POLICY notes_own ON app.notes
  FOR ALL
  TO app_user
  USING (owner = current_user)
  WITH CHECK (owner = current_user);
USING filters reads. WITH CHECK blocks INSERT/UPDATE that would store someone else’s owner. Test as app_user, not as postgres — the owner bypasses RLS.
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE app.secrets (
  id      bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  pw_hash text NOT NULL,
  card    bytea NOT NULL
);

INSERT INTO app.secrets (pw_hash, card) VALUES (
  crypt('lab_only', gen_salt('bf')),
  pgp_sym_encrypt('4111111111111111', 'study_lab_key')
);

SELECT crypt('lab_only', pw_hash) = pw_hash AS pw_ok,
       pgp_sym_decrypt(card, 'study_lab_key') AS card
FROM app.secrets;
bf is Blowfish (bcrypt-style) for crypt. pgp_sym_encrypt returns bytea. Anyone with SELECT on app.secrets and the key can decrypt — GRANT still matters.

5. Production perspective

🏭 Production note. One role per app, not per developer, unless you have a reason. Revoke CREATE on public if it is still granted. Prefer ALTER DEFAULT PRIVILEGES so future tables stay locked down.

6. Hands-on lab

Add to pg_hba.conf (then reload):

host    study_lab    app_user    192.168.56.0/24    scram-sha-256
host    study_lab    app_user    127.0.0.1/32       scram-sha-256

sudo pg_ctlcluster 18 main reload
sudo -u postgres psql -d study_lab -f - <<'SQL'
CREATE ROLE app_user LOGIN PASSWORD 'app_user_lab_only';
GRANT CONNECT ON DATABASE study_lab TO app_user;
-- deliberately skip schema USAGE first
GRANT SELECT ON app.users TO app_user;
SQL

Connect and fail:

psql -h 127.0.0.1 -U app_user -d study_lab -c "SELECT * FROM app.users;"
# expected: permission denied for schema app

Fix:

sudo -u postgres psql -d study_lab -c "GRANT USAGE ON SCHEMA app TO app_user;"
psql -h 127.0.0.1 -U app_user -d study_lab -c "SELECT email FROM app.users;"

Then RLS on app.notes (as postgres, then test as app_user):

sudo -u postgres psql -d study_lab -f - <<'SQL'
CREATE TABLE app.notes (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  owner name NOT NULL DEFAULT current_user,
  body text NOT NULL
);
GRANT SELECT, INSERT ON app.notes TO app_user;
GRANT USAGE, SELECT ON SEQUENCE app.notes_id_seq TO app_user;
ALTER TABLE app.notes ENABLE ROW LEVEL SECURITY;
CREATE POLICY notes_own ON app.notes
  FOR ALL TO app_user
  USING (owner = current_user)
  WITH CHECK (owner = current_user);
INSERT INTO app.notes (owner, body) VALUES
  ('app_user', 'visible to app_user'),
  ('lab_admin', 'hidden from app_user');
SQL

psql -h 127.0.0.1 -U app_user -d study_lab -c "SELECT owner, body FROM app.notes;"
# one row: app_user / visible to app_user

psql -h 127.0.0.1 -U app_user -d study_lab \
  -c "INSERT INTO app.notes (owner, body) VALUES ('lab_admin', 'nope');"
# expected: new row violates row-level security policy

psql -h 127.0.0.1 -U app_user -d study_lab \
  -c "INSERT INTO app.notes (body) VALUES ('mine');"
# works — owner defaults to current_user

Column encryption (as postgres):

sudo -u postgres psql -d study_lab -f - <<'SQL'
CREATE EXTENSION IF NOT EXISTS pgcrypto;
CREATE TABLE app.secrets (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  pw_hash text NOT NULL,
  card bytea NOT NULL
);
INSERT INTO app.secrets (pw_hash, card) VALUES (
  crypt('lab_only', gen_salt('bf')),
  pgp_sym_encrypt('4111111111111111', 'study_lab_key')
);
SELECT crypt('lab_only', pw_hash) = pw_hash AS pw_ok,
       pgp_sym_decrypt(card, 'study_lab_key') AS card

8. Troubleshooting

Symptom

password authentication failed vs permission denied for table.

Diagnosis

First is pg_hba / password / role LOGIN. Second is GRANT. Read the error. They are not the same ticket.

9. Exam focus

🔥 Exam focus. Auth ≠ privileges. Schema USAGE. pg_hba first match. RLS: ENABLE then CREATE POLICY. Encryption: CREATE EXTENSION pgcrypto — one-way crypt, two-way pgp_sym_encrypt. Not TDE.

10. One-minute revision

  • app_user can read app.users after USAGE + SELECT.
  • audit stays locked.
  • Failed-then-fixed lab is the lesson.
  • RLS: ENABLE + CREATE POLICY … USING … WITH CHECK on app.notes.
  • pgcrypto: crypt (one-way) vs pgp_sym_encrypt (two-way).

Review questions

Q1. Why did SELECT fail before schema USAGE even with table GRANT?

PostgreSQL checks schema usage before object privileges. No USAGE, no name lookup.

Q2. RLS is enabled, no policy exists, you connect as app_user with SELECT. What do you see?

Zero rows. Deny by default. The owner/superuser still sees everything unless FORCE ROW LEVEL SECURITY.

Q3. Which clause stops app_user from inserting owner = 'lab_admin'?

WITH CHECK (owner = current_user). USING only filters rows that already exist.

Q4. Community PostgreSQL encrypts the whole data directory if you CREATE EXTENSION pgcrypto. True / False?

False. pgcrypto is selected columns. At-rest of PGDATA is OS/volume encryption (or a vendor extra), not this extension.
