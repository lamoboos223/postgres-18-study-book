Chapter 13 · EDB: Routine Maintenance Tasks

VACUUM, ANALYZE, bloat, wraparound

MVCC leftover versions do not vanish at COMMIT. VACUUM is the janitor. Autovacuum is that janitor on a timer. VACUUM FULL is a rewrite, not “better VACUUM.”

1. What you need to know

VACUUM marks dead tuples reusable and updates the visibility map. ANALYZE refreshes planner stats. VACUUM FREEZE advances relfrozenxid to avoid transaction-ID wraparound. REINDEX rebuilds indexes. VACUUM FULL rewrites the table (ACCESS EXCLUSIVE, extra disk).

2. Mental model

UPDATE / DELETE
▼
Dead row versions still on the page
▼ VACUUM
Space reusable for new versions
▼ VACUUM FULL (rarely)
New file, old file dropped · locks everyone

3. Deep explanation

Autovacuum launcher starts workers per table based on dead-tuple scale factors. If it cannot keep up (long transactions, too few workers, throttling), tables bloat. Wraparound: if relfrozenxid gets too old, PostgreSQL will eventually refuse writes — freeze vacuum is mandatory, not optional hygiene.

SQL Server has no VACUUM because it does not keep heap versions the same way. Do not look for a SQL Server twin.

vacuumdb is the shell wrapper — vacuumdb --all hits every database. Also know CLUSTER (rewrite a table in index order; exclusive lock). Autovacuum needs track_counts = on. Temp tables are never autovacuumed.

v17+ exam bait: vacuum is no longer capped at 1 GB of maintenance_work_mem; it uses an adaptive radix tree, writes less WAL (freeze + prune can share a record), and you can cap its buffer use with vacuum_buffer_usage_limit / VACUUM (BUFFER_USAGE_LIMIT …) / vacuumdb --buffer-usage-limit.

4. PostgreSQL 18 example

VACUUM (VERBOSE) app.orders;
ANALYZE app.orders;
VACUUM (FREEZE, VERBOSE) app.orders;
VERBOSE prints what the janitor did. Regular VACUUM does not shrink the file to the OS; it makes space reusable internally.

5. Production perspective

🏭 Production note. Watch pg_stat_progress_vacuum, n_dead_tup, wraparound age. Do not schedule VACUUM FULL nightly “just in case.” Fix the workload or fillfactor / HOT updates first.

6. Hands-on lab

sudo -u postgres psql -d study_lab

-- bloat demo on a copy, not production
CREATE TABLE app.orders_bloat AS TABLE app.orders;
INSERT INTO app.orders_bloat SELECT * FROM app.orders_bloat; -- grow if needed
UPDATE app.orders_bloat SET status = status;
SELECT n_live_tup, n_dead_tup, last_vacuum, last_autovacuum
FROM pg_stat_user_tables WHERE relname = 'orders_bloat';
VACUUM (VERBOSE) app.orders_bloat;
SELECT n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname = 'orders_bloat';
⚠️ Destructive. VACUUM FULL app.orders; locks the real orders table. Skip FULL on app.orders. If you try FULL, use orders_bloat only.

8. Troubleshooting

Symptom

Table grows forever; autovacuum seems idle.

Investigation

SELECT pid, state, xact_start, query FROM pg_stat_activity WHERE state = 'idle in transaction';
SELECT relname, n_dead_tup, vacuum_count, autovacuum_count FROM pg_stat_user_tables;

Fix

Kill or commit the old transaction. Then VACUUM. Then ask why the app left a session open.

9. Exam focus

🔥 Exam focus. VACUUM vs VACUUM FULL vs ANALYZE vs REINDEX vs vacuumdb. Wraparound: vacuum every ~2 billion xids. vacuum_freeze_min_age / vacuum_freeze_table_age. v17+ dropped the 1 GB vacuum mem cap.
Remember. VACUUM = reclaim visibility leftovers for normal operation. VACUUM FULL = rewrite.

10. One-minute revision

  • Dead tuples → VACUUM → reuse.
  • ANALYZE → planner.
  • FULL is a last resort.

Review questions

Q1. After VACUUM, du on the file did not drop. Is VACUUM broken?

Usually no. Regular VACUUM returns pages to the table’s free space map, not necessarily to the OS.
