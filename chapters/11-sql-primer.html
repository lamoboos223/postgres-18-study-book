Chapter 11 · EDB: SQL Primer

Transactions, indexes, EXPLAIN — DBA-flavored SQL

You already know SELECT. This chapter is the SQL a DBA must defend: isolation, indexes, and reading a plan.

1. What you need to know

Default isolation is READ COMMITTED. Transactions are BEGIN / COMMIT / ROLLBACK. Indexes are separate objects. EXPLAIN (ANALYZE, BUFFERS) runs the query and shows what it did.

3. Deep explanation

B-tree is the default index. Use it for equality and ranges. Other types exist (GIN for jsonb, GiST, BRIN) — know they exist for Essentials; do not invent syntax you have not looked up.

EXPLAIN without ANALYZE is an estimate only. With ANALYZE it executes (so a DELETE plan would delete — wrap in a transaction and rollback, or use EXPLAIN on SELECT).

Transactions: a second session may or may not see your uncommitted rows (it will not, under default isolation). Row-level locks appear on UPDATE/DELETE.

4. PostgreSQL 18 example

CREATE TABLE app.order_items (
  id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  order_id   bigint NOT NULL REFERENCES app.orders(id),
  product_id bigint NOT NULL REFERENCES app.products(id),
  qty        int NOT NULL CHECK (qty > 0)
);

CREATE TABLE app.messages (
  id      bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL REFERENCES app.users(id),
  body    text NOT NULL,
  sent_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO app.order_items (order_id, product_id, qty) VALUES (1, 1, 2);
CREATE INDEX ON app.users (email);
CREATE INDEX ON app.messages (user_id, sent_at DESC);

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM app.users WHERE email = 'ada@example.com';
CREATE INDEX ON app.users (email) builds a B-tree. Unique constraint on email already created an index — a second index may be redundant. Notice that in \d app.users.

5. Production perspective

🏭 Production note. Every index slows writes and needs VACUUM/maintenance. Missing index on a hot FK is a classic outage pattern. CREATE INDEX CONCURRENTLY avoids a long ACCESS EXCLUSIVE lock — Essentials: know why people use it.

6. Hands-on lab

Session 1:

BEGIN;
UPDATE app.products SET price = 11.00 WHERE sku = 'SKU-1';
-- leave open

Session 2:

SELECT price FROM app.products WHERE sku = 'SKU-1';
-- sees old price under READ COMMITTED until session 1 commits
-- UPDATE the same row here to see a lock wait

SELECT * FROM pg_locks WHERE NOT granted;

Session 1: COMMIT;

8. Troubleshooting

Symptom

Seq Scan on a huge table for a selective WHERE.

Investigation

EXPLAIN (ANALYZE, BUFFERS) ...
SELECT relname, last_analyze, n_live_tup FROM pg_stat_user_tables;

Fix

Add the right index, ANALYZE the table, rewrite the predicate so it is sargable (no function wrapping the column if you can avoid it).

9. Exam focus

🔥 Exam focus. Default isolation. WAL on commit. Index types at a name-recognition level. EXPLAIN ANALYZE executes. Transactions are not “just autocommit vs not” — know BEGIN/COMMIT.

Review questions

Q1. True / False. EXPLAIN ANALYZE DELETE FROM app.users; is safe because EXPLAIN never changes data.

False. ANALYZE executes the plan. That DELETE would delete. Use a transaction and ROLLBACK, or EXPLAIN a SELECT.
