Chapter 2 · EDB: System Architecture

Processes, memory, MVCC, WAL, checkpoints

This is the chapter that turns “Postgres is a server” into “I can explain why a commit is durable, why readers do not block writers, and why disk fills with WAL.” You still do not install PostgreSQL here. After Chapter 3 you come back and look at the live processes.

1. What you need to know

One cluster has:

  • A supervisor postgres process (still often called postmaster).
  • Backend processes — one per client connection.
  • Background processes — checkpointer, background writer, WAL writer, autovacuum launcher, stats collector / logger, and in PostgreSQL 18 I/O workers when io_method = worker.
  • Shared memory — especially shared_buffers (cached 8 kB pages).
  • WAL in pg_wal — the durable diary of changes.
  • Data files — heap and index pages; they may be dirty in memory until a checkpoint.

MVCC means readers see a snapshot. Updates create new row versions. Dead versions stay until VACUUM (Chapter 13).

3. Deep explanation

Why shared buffers exist

Backends do not read every row from disk on every query. They pin 8 kB pages in shared_buffers. A write first updates the in-memory page and appends WAL. The data file can lag. That is why “the table file looks old” after a commit is normal.

Why WAL exists

If PostgreSQL wrote data pages first and crashed mid-write, you would have torn pages and no way to know the commit order. WAL is sequential and flushed on commit (when synchronous_commit is on, the default). Recovery replays WAL. Official name: Write-Ahead Log. SQL Server analogue: the transaction log — similar job, different file layout and tools.

Checkpointer vs background writer

The checkpointer starts a checkpoint: flush dirty buffers so a new recovery starting point exists, then update control data. The background writer slowly writes dirty buffers between checkpoints so backends are less likely to stall finding a free buffer. Official docs: bgwriter can increase total I/O because a hot page may be written more than once per checkpoint interval.

MVCC vs SQL Server

PostgreSQL writers create new versions; readers do not take shared locks on rows for a normal SELECT. SQL Server historically used locking; later versions added row-versioning isolation. Do not say “Postgres has no locks” — it has plenty (pg_locks). It just does not lock readers the SQL Server default way.

PostgreSQL 18 note. io_method selects how asynchronous-eligible reads run: worker (default, I/O worker processes), io_uring (Linux, needs a build with liburing), or sync (do those I/Os synchronously). It is set at server start only. WAL and commit durability are still synchronous write-ahead logging. AIO does not mean “commits skip fsync.”

4. PostgreSQL 18 example

Run these after Chapter 3. Learn the names now.

ps -u postgres -o pid,cmd
# or: sudo pstree -p $(pgrep -o postgres)
ps lists processes owned by the OS user postgres. You should see one supervisor and several helpers. Each psql session adds a backend line.
psql -d postgres -c "SHOW shared_buffers;"
psql -d postgres -c "SHOW wal_level;"
psql -d postgres -c "SHOW io_method;"
psql -d postgres -c "SHOW io_workers;"
SHOW reads the live setting. On PostgreSQL 18, wal_level defaults to replica. io_method defaults to worker. Changing io_method requires a restart.
psql -d postgres -c "SELECT pid, backend_type, wait_event_type, wait_event FROM pg_stat_activity ORDER BY backend_type;"
pg_stat_activity is the process table for the cluster. backend_type distinguishes client backends from checkpointer, walwriter, and I/O workers.

5. Production perspective

🏭 Production note. shared_buffers is not “set to 80% of RAM.” Typical starting range is a fraction of RAM (often ~25% as a conversation starter, then measure). Connections each cost a backend process. WAL disk is a first-class volume: if WAL cannot flush, commits stall.
  • Performance: cache hits live in shared buffers + OS page cache. Sequential read-heavy work is where PG 18 AIO is aimed (scans, vacuum), not “make COMMIT skip WAL.”
  • Reliability: disable fsync only in throwaway labs. Never in production.
  • Failure: filling the WAL volume stops the cluster. Filling the data volume does too.

8. Troubleshooting

Symptom

After Chapter 3, commits are slow and pg_stat_activity shows WALWrite / IO waits.

Possible causes

  • WAL on a slow or full disk.
  • synchronous_commit=on (default) on terrible storage — expected durability cost.
  • Another process saturating the disk.

Investigation

df -h /var/lib/postgresql
psql -d postgres -c "SHOW data_directory;"
psql -d postgres -c "SELECT wait_event_type, wait_event, count(*) FROM pg_stat_activity GROUP BY 1,2 ORDER BY 3 DESC;"

Fix

Free WAL disk. Do not turn off fsync to “fix” production. Move WAL only with a planned layout (later chapters).

Verification

Commits return quickly and df shows free space on the WAL filesystem.

9. Exam focus

🔥 Exam focus. Commit durability = WAL flush. Crash recovery = replay WAL from last checkpoint. MVCC = extra versions, not in-place overwrite. wal_level default in modern PostgreSQL is replica (enough for replication and hot standby). Old names archive / hot_standby map to replica.
Remember. WAL = diary. Checkpoint = photo. VACUUM = janitor for dead versions. AIO (PG 18) = faster reads, not optional durability.

10. One-minute revision

  • Supervisor forks backends; helpers write WAL, dirty pages, checkpoints.
  • Pages live in shared_buffers first.
  • COMMIT flushes WAL. Checkpoint flushes data pages.
  • MVCC keeps old row versions until VACUUM.
  • PG 18: io_method is worker by default; restart to change.

Review questions

Q1. A backend commits. Which must be on disk before PostgreSQL reports success (default synchronous_commit)?

  1. Every dirty heap page for that table
  2. The WAL records for the commit
  3. A completed checkpoint
  4. An autovacuum run

Answer: B. Heap pages may still be dirty in shared buffers. Checkpoint is periodic. Autovacuum is unrelated to commit acknowledgement.

Q2. True / False. PostgreSQL 18 asynchronous I/O means COMMIT no longer writes WAL.

False. AIO is for eligible reads. WAL remains the write-ahead path for durability.

Q3. What happens if the server crashes after COMMIT returned but before the next checkpoint?

On restart, PostgreSQL recovers from the last checkpoint and replays WAL, including that commit. The transaction stays committed.
