Chapter 12 · EDB: Backup, Recovery and Point-in-Time Recovery

pg_dump is not a replica, and WAL is not optional for PITR

Logical backup copies SQL-restoreable objects. Physical backup copies the cluster files. PITR needs a base backup plus archived WAL.

1. What you need to know

pg_dump / pg_dumpall = logical. pg_basebackup = physical of a running cluster (replication protocol; needs REPLICATION privilege or superuser, and a free WAL sender). Restore of a dump is pg_restore or psql depending on format.

A backup is a point-in-time copy. A replica is a running second server replaying WAL.

3. Deep explanation

A dump does not include uncommitted work and is not crash-consistent the way a base backup + WAL is. It is excellent for logical copies and migrations. Physical backup is what you need for PITR and for building standbys (Chapter 15).

PITR: enable archive_mode, set archive_command (or archive_library), take pg_basebackup, keep WAL segments. Restore files, configure recovery to a timestamp, start. wal_level must be replica or higher (default). Official docs: minimal is not enough for PITR / streaming.

Formats: pg_dump -Fc custom (pg_restore, parallel). -f file.sql plain (psql).

PITR restore (EDB steps, compressed): stop the server, empty PGDATA, copy the base backup in, set restore_command, drop a recovery.signal file in PGDATA, start. The server removes recovery.signal when recovery finishes. Targets: recovery_target_time / xid / name. standby.signal is different — that one means “stay a replica.”

Incremental physical backups (v17+): set summarize_wal = on, take a full pg_basebackup (writes backup_manifest), then pg_basebackup --incremental=…/backup_manifest. Restore: pg_combinebackup full + incrementals into one tree, then start (or PITR). Check a backup with pg_verifybackup. The WAL summarizer writes tiny files under pg_wal/summaries/; pg_walsummary dumps them.

SHOW summarize_wal;   -- must be on
sudo -u postgres pg_basebackup -D /var/lib/postgresql/backups/full -Fp -Xs -P
sudo -u postgres pg_basebackup -D /var/lib/postgresql/backups/incr1 \
  --incremental=/var/lib/postgresql/backups/full/backup_manifest -Fp -Xs -P
sudo -u postgres pg_combinebackup \
  /var/lib/postgresql/backups/full /var/lib/postgresql/backups/incr1 \
  -o /var/lib/postgresql/backups/combined
sudo -u postgres pg_verifybackup /var/lib/postgresql/backups/full

EDB also names Barman and pgBackRest as production backup tools. Know they exist; this lab stays on pg_basebackup.

4. PostgreSQL 18 example

sudo -u postgres pg_dump -d study_lab -Fc -f /tmp/study_lab.dump
sudo -u postgres pg_dump -d study_lab -f /tmp/study_lab.sql
sudo -u postgres pg_basebackup -D /tmp/basebak -Fp -Xs -P
-Fc custom format. -D destination directory for a physical copy. -Fp plain files. -Xs stream WAL with the backup so the copy is consistent. -P progress.

5. Production perspective

🏭 Production note. Test restore on another machine. A backup you have never restored is a rumor. Retention must cover your RPO. Encryption and off-site copies are operations, not optional extras.

6. Hands-on lab

sudo -u postgres mkdir -p /var/lib/postgresql/backups /var/lib/postgresql/wal_archive
sudo -u postgres pg_dump -d study_lab -Fc -f /var/lib/postgresql/backups/study_lab.dump

Logical restore into a throwaway database:

sudo -u postgres psql -d postgres -c "CREATE DATABASE study_lab_restore OWNER lab_admin;"
sudo -u postgres pg_restore -d study_lab_restore /var/lib/postgresql/backups/study_lab.dump
sudo -u postgres psql -d study_lab_restore -c "SELECT count(*) FROM app.users;"
⚠️ Destructive if you restore over study_lab. We restore into study_lab_restore only.

Physical backup (lab copy, not a standby yet):

sudo -u postgres pg_basebackup -h 127.0.0.1 -U postgres -D /var/lib/postgresql/backups/base_main -Fp -Xs -P

Optional mini PITR (archive to a folder). In postgresql.conf:

archive_mode = on
archive_command = 'test ! -f /var/lib/postgresql/wal_archive/%f && cp %p /var/lib/postgresql/wal_archive/%f'

Restart after archive_mode (it is a restart parameter), then SELECT pg_switch_wal(); and confirm a file landed in the archive directory.

8. Troubleshooting

Symptom

pg_basebackup fails with replication / WAL sender errors.

Possible causes

  • max_wal_senders exhausted (default 10 — lab should be fine).
  • pg_hba missing a replication line if you used a non-superuser.
  • Destination directory exists and is not empty.

Fix

Use an empty -D. Superuser local backup should work. For a dedicated user, CREATE ROLE ... REPLICATION LOGIN and a host replication pg_hba line.

Review questions

Q1. You have only last night’s pg_dump. Can you restore to 10:17 this morning?

No. That is a logical snapshot of dump time. PITR needs physical backup + WAL after that backup.

Q2. Incremental restore: do you start the incremental directory as PGDATA?

No. Combine first: pg_combinebackup full + incrementals, then treat the output as the base. Needs summarize_wal=on when the incrementals were taken.
