Chapter 15 · EDB: Replication and High Availability Tools

Streaming replication from pg-primary to pg-standby

Now the second VM earns its keep. Physical streaming: WAL over the network, replay on the standby, optional sync, promote in the lab only.

1. What you need to know

Physical replication copies the cluster (all databases). Logical replication copies selected changes as rows (Advanced-level depth). Essentials: streaming physical + why slots exist.

Official defaults you should remember: wal_level = replica, max_wal_senders = 10, hot_standby = on. Old GUC names archive / hot_standby as wal_level values map to replica.

3. Deep explanation

A replication slot stores how far a standby has confirmed WAL. The primary will not recycle those segments. That prevents “standby needs WAL that is gone.” It also means a forgotten slot fills the disk with WAL.

pg_basebackup can stream WAL (-Xs) and can use -R to write postgresql.auto.conf + standby.signal so the copy starts as a standby.

Lag: sent_lsn vs replay_lsn in pg_stat_replication. Received but not replayed = apply lag (queries, conflicts, IO).

Hot standby conflicts: VACUUM on primary vs long query on standby. hot_standby_feedback reduces cleanup conflicts and can bloat the primary.

Cascading: a standby can stream to another standby (primary_conninfo points at the upstream replica). Async only. Offloads the primary. Other standby GUCs the deck wants named: primary_slot_name, max_standby_streaming_delay, wal_receiver_create_temp_slot, recovery_min_apply_delay (delayed replica).

WAL retention without a slot: wal_keep_size. Cap a slot’s disk use: max_slot_wal_keep_size. Sync needs synchronous_standby_names; if that standby dies, COMMITs wait unless you set synchronous_commit to local or off.

Logical replication: CREATE PUBLICATION … FOR TABLE … on the publisher, CREATE SUBSCRIPTION … CONNECTION '…' PUBLICATION … on the subscriber. Row-level, selected tables, can cross versions. Subscriber tables are read-only in practice. Needs wal_level = logical.

HA tool names (skip the sales slides): repmgr / repmgrd, EDB Failover Manager (EFM), Patroni, HARP, EDB Postgres Distributed. This lab promotes by hand.

4. PostgreSQL 18 example

-- on primary
CREATE ROLE replicator LOGIN REPLICATION PASSWORD 'replicator_lab_only';
SELECT pg_create_physical_replication_slot('standby1');
REPLICATION is a role attribute. The slot name is what the standby will use as primary_slot_name.

5. Production perspective

🏭 Production note. Monitor slot age and disk. Async replicas can lose recent commits on failover. Sync reduces that window and adds commit latency / availability coupling. Two nodes is not a full HA story (no auto-fencing). RPO/RTO belong in the runbook.

6. Hands-on lab

On pg-primary

Confirm (defaults are usually enough):

sudo -u postgres psql -d postgres -c "SHOW wal_level;"
sudo -u postgres psql -d postgres -c "SHOW max_wal_senders;"

Add to pg_hba.conf and reload:

host    replication    replicator    192.168.56.11/32    scram-sha-256

sudo -u postgres psql -d postgres -c "CREATE ROLE replicator LOGIN REPLICATION PASSWORD 'replicator_lab_only';"
sudo -u postgres psql -d postgres -c "SELECT pg_create_physical_replication_slot('standby1');"

On pg-standby

Install PostgreSQL 18 the same PGDG way as Chapter 3, then stop and empty the data directory. You cannot stream into a second independent initdb.

sudo pg_ctlcluster 18 main stop
sudo rm -rf /var/lib/postgresql/18/main/*
⚠️ DESTRUCTIVE on pg-standby only. This deletes the standby’s local cluster. Never run this on pg-primary. 
sudo -u postgres pg_basebackup \
  -h 192.168.56.10 -U replicator -D /var/lib/postgresql/18/main \
  -Fp -Xs -P -R --slot=standby1
-h primary. -U replicator replication user. -D new PGDATA. -R writes standby config. --slot=standby1 uses the slot during WAL stream (pairs with -Xs).

Debian still needs config in /etc/postgresql/18/main pointing at that data directory (package default already does). Start:

sudo pg_ctlcluster 18 main start

If -R wrote primary_conninfo into the data directory, you are streaming. Set primary_slot_name = 'standby1' in the standby config if it is not already there, then reload/restart the standby.

8. Troubleshooting

Symptom

Standby is running but pg_stat_replication is empty.

Possible causes

  • pg_hba database field must be replication, not study_lab.
  • Wrong password / replicator lacks REPLICATION.
  • Standby has no standby.signal / is not in recovery.
  • Firewall between .10 and .11.

Investigation

sudo tail -n 50 /var/log/postgresql/postgresql-18-main.log
# on both VMs

Symptom: WAL growing on primary

Slot inactive. Either start the standby or SELECT pg_drop_replication_slot('standby1'); after you accept data loss for that copy.

9. Exam focus

🔥 Exam focus. Physical vs logical (pub/sub). Cascading is async. Slot vs wal_keep_size. standby.signal. Sync can stall COMMITs. Promote is not EFM/repmgr.

Review questions

Q1. Scenario. Standby receives WAL but replay is delayed. What do you inspect?

pg_stat_replication.replay_lsn vs sent_lsn / flush_lsn. Standby pg_stat_activity (queries blocking apply). Logs for recovery conflicts. Disk IO on the standby.

Q2. What happens if you promote the standby while the old primary is still accepting writes?

You can get split-brain: two writers, diverging timelines. Lab: stop the old primary first (or fence it). This is why HA tools exist.

Q3. True / False. hot_standby=on (default) lets you run read-only SQL on a standby in recovery.

True. It is a restart-level parameter and only matters during recovery/standby mode.
